# delivery-adapter

The adapter between the commerce API and the third-party delivery apps. It
does three things:

1. **Inbound webhooks.** A partner tells us an order was placed or
   cancelled. We verify the signature, drop duplicates by the partner's
   event id, and hand the order to the commerce API.
2. **Outbound menu sync.** When a menu changes, we push each store's menu
   to the partner in the partner's shape.
3. **Retries.** Everything outbound goes through an outbox. A failed call
   is retried; a job that runs out of attempts lands in the dead-letter
   list, visible on `/health`.

Partners today: Hopbasket and Platefast. Nothing here talks to a real partner: the clients
take a `fetch` and the tests pass in a recorded one.

## Running it

```
npm ci
cp .env.example .env
npm run dev
```

The service listens on `PORT` (default 8090). `GET /health` reports the
outbox counts.

## Environment variables

See `.env.example`. `HOPBASKET_WEBHOOK_SECRET` and `PLATEFAST_WEBHOOK_SECRET` are the shared keys
the partners sign webhooks with; a request with a bad signature is rejected before the
body is read as an event. `COMMERCE_API_TOKEN` is the service token for
the commerce API. The outbox retry settings are read once at start.

## Tests

| Command | Runs |
|---|---|
| `npm test` | everything |
| `npm run test:unit` | unit tests under `src/` (idempotency, signature, outbox, mappers, ingestion) |
| `npm run test:contract` | contract tests under `contracts/`, against the recorded partner responses |

The recorded responses are versioned by partner API version; see
`contracts/README.md` for how a recording is made and when a new folder is
cut.

## Pipeline

`.github/workflows/ci.yml` installs, compiles, lints, checks formatting and
runs both test tiers on every change and on `main`. There is no deploy job:
release tags are promoted to the fleet by the store systems team's tooling,
outside this repository.

## Layout

```
src/
  server.ts        Fastify app: routes, logging, raw-body JSON parser
  app.ts           wires config, clients, outbox and services together
  main.ts          starts the server and the outbox worker
  config.ts        environment parsing
  contracts/       zod schemas for each partner's payloads (what we accept)
  webhooks/        inbound: the shared verify-dedupe-handle flow and one thin route per partner
  menu-sync/       outbound: our menu shape and the per-partner mappers
  orders/          order ingestion into the commerce API (stub client)
  outbox/          the retrying outbox and its dead-letter list
  partners/        outbound HTTP clients, one per partner
contracts/         recorded partner responses and the tests that pin them
```
